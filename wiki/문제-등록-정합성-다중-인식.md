# 문제 등록 정합성·다중 인식

> 한 장에 여러 문제, 한 문제가 여러 장, AI 오분류·오판단, 동시 업로드, 느린 외부 AI, 남의 요청 — 이 모든 변수 속에서 **"쓰레기·중복·유령 데이터 없이" 질문을 등록**하기 위한 규칙(R1~R6)·캐시·트랜잭션·접근 제어 설계.

## 한눈에 보기

| 항목 | 내용 |
|---|---|
| 등록 규칙 | R1~R6 (상한 · 감지 0건 · 과목혼합 · 최소길이 · 언어보정 · 과목결정) |
| OCR 모드 | `SINGLE_MULTIPAGE`(한 문제 여러 장) / `MULTI_PROBLEM`(여러 문제) + **서버 측 모드 검증** |
| 다중 감지 캐시 | `DetectionCache` 인메모리 · TTL 10분 · 재OCR 없음 · **학생별로 묶고 원자적으로 꺼냄** |
| 정합성 | 상한 확인+INSERT(**항상 새 트랜잭션** · SERIALIZABLE) · 분석 마감 150s · Idempotency-Key(등록·선택) |
| 접근 제어 | JWT 인증 주체 · 본인 질문만 조회·수정·취소 |
| 이미지 정리 | 저장 전 실패 즉시 삭제(`committed`) · 선택 제외 장 1시간 유예 삭제 · 10분 주기 청소 |

## 문제 상황

처음 설계할 때 다룬 문제:

- 한 장에 **여러 문제**가 섞여 들어오면 어떤 문제를 등록할지 모호하고, 잘못 등록하면 강사 매칭이 엉킴.
- 한 **문제가 여러 장**에 걸치면(지문+문항 분리) 페이지 순서를 맞추고 본문을 조합해야 함.
- 외부 AI(Gemini)가 **과목을 틀리게 판정**(영어 지문을 국어로 등)하는 경우가 있음.
- 같은 학생이 **동시에 여러 번 업로드**하면 "진행 중 질문 상한"을 넘겨버리는 경합(race condition).
- OCR·분류가 재시도로 길어져 **프론트는 타임아웃(실패)인데 서버는 등록을 커밋**하는 불일치.
- 네트워크 재시도로 **같은 등록 요청이 중복** 도착.
- 선택 안 된/실패한 이미지가 S3에 **삭제되지 않은 채** 남음(참조 없는 URL).

이후 코드를 다시 점검하며 발견해 고친 문제:

- 문제 API가 `permitAll`이고 학생 ID를 **요청값으로** 받아, 로그인 없이 **남의 질문을 조회·수정·취소**하거나 남의 ID로 등록할 수 있었음. 상한(R1)도 ID만 바꾸면 무의미했음.
- 선택 확정(`/select`) 경로에서는 **SERIALIZABLE이 적용되지 않았음** — 호출부 트랜잭션에 합류하면 격리 수준이 무시되기 때문.
- 같은 선택이 **동시에 두 번** 들어오면 캐시를 둘 다 읽어 **문제가 두 건** 생길 수 있었음.
- 선택 인덱스를 담아 **다시 업로드하는 레거시 경로**가 재OCR 결과와 어긋나 다른 문제를 저장할 수 있었음.
- 서버가 **모델의 모드 판단을 거의 검증하지 않아**, 장이 빠진 채 등록되거나 여러 문제가 한 문제로 묶여 R3를 건너뛸 수 있었음.
- 선택 시 모델이 매긴 **장 번호가 틀리면 고른 문제의 실제 이미지가 즉시 삭제**되어 복구할 수 없었음.

## 해결 방법

등록 요청이 거치는 **분기 전체 흐름과 단계별 동작**은 [문제 등록 / OCR — 핵심 로직 / 분기](./문제-등록-OCR.md#핵심-로직--분기)에 정리했다. 이 문서는 **각 장치가 왜 필요한가**에 집중한다.

### 접근 제어 — 모든 규칙의 전제

R1(상한)도, 선택 캐시도, 소유권도 **"요청한 사람이 누구인가"를 믿을 수 있어야** 의미가 있다.

- 학생·강사 ID는 **JWT 인증 주체**(`@AuthenticationPrincipal`)에서만 가져온다. 요청 body·쿼리의 ID는 사용하지 않는다.
- `SecurityConfig`에서 역할별로 막는다 — 탐색 목록은 강사, 단건 조회는 로그인 사용자, 나머지는 학생.
- `ProblemService.findOwnedProblem()`이 조회·분류 수정·순서 변경·취소 대상이 **본인 질문인지** 확인한다(아니면 403).
- 여러 문제 감지 결과는 **업로드한 학생에게 묶어** 캐시하고, 다른 학생이 `detectionId`로 선택하면 403.

### 모드 판별과 서버 측 검증

- **SINGLE_MULTIPAGE** — 한 문제가 여러 장에 걸침. `suggestedOrder`대로 이미지를 정렬하고 장별 텍스트(`pageTexts`)를 보관 → 이후 드래그 재정렬 시 **재OCR 없이** `pageTexts`만 새 순서로 재조합(`Problem.reorderPages`).
- **MULTI_PROBLEM** — 그 외 전부. 1개면 자동 등록, 여러 개면 선택 흐름으로.

이 판단 하나에 선택 화면 생략과 R3 생략이 걸려 있어서, **구조적으로 성립하지 않는 판단은 서버가 바로잡거나 거부한다.**

| 모델 응답 | 처리 |
|---|---|
| 이미지 1장인데 `SINGLE_MULTIPAGE` | `MULTI_PROBLEM`으로 보정 |
| 장별 텍스트가 이미지와 1:1이 아님 | 거부 — 등록 후 본문을 고칠 수단이 없어, 조용히 누락되면 복구할 수 없다 |
| 두 장 이상에 선택지(①) · EBS 코드 2종 이상 | 거부 — 여러 문제가 묶인 신호. 문제별로 나눠 올리도록 안내 |

### 다중 감지 → 선택 (`DetectionCache`)

- OCR은 비싸므로(돈·수 초), 여러 문제 감지 후 학생이 고르기 전까지 **1차 결과를 그대로 보관**하고 `detectionId`(교환권)만 응답.
- `POST /problems/select`가 `detectionId`로 캐시에서 꺼내 **고른 문제만 저장** → 재OCR·재업로드 없음.
- **꺼내는 순간 제거한다**(`take`, `ConcurrentHashMap.remove`). 같은 선택이 동시에 두 번 와도 한 요청만 항목을 받는다. 저장에 실패하면 `restore`로 되돌려 다시 고를 수 있다.
- 컨트롤러는 `detectionId`를 멱등 키로 써서, 두 번째 요청에 에러 대신 **처음 결과를 그대로** 돌려준다.
- 인메모리 + TTL 10분. *재시작·다중 인스턴스엔 안 남음 — MVP 허용, 추후 Redis로 이전 여지.*

### 등록 규칙 R1~R6

`createProblem` → `saveProblem` 경로에서 **입구 가드(guard clause)** 로 나쁜 케이스를 순서대로 걸러낸다.

| 규칙 | 검증 | 막는 상황 | 설계 의도 |
|---|---|---|---|
| **R1** | 진행 중(PENDING) 질문 3개 미만 | 질문 도배 | 강사 풀 보호·비용 통제. **OCR 전** 사전 차단 + 저장 시 재확인. 학생 ID를 토큰에서 가져오므로 우회할 수 없다 |
| **R2** | 감지 문제 ≥ 1개 | 빈 종이·풍경 사진 | 쓰레기 데이터 차단 |
| **R3** | 서로 다른 과목 < 3종 | 여러 과목 뒤섞인 사진 | OCR/분류 정확도 급락 방지 → 나눠 올리기 유도 |
| **R4** | 추출 텍스트 ≥ 10자 | 글씨 안 보이는 흐린 사진 | "문제 글"이 실제로 있어야 등록 |
| **R5** | 언어 휴리스틱(라틴 ≥ 한글×4 & ≥20자 → ENGLISH) | AI가 영어를 국어로 오인식 | 과분류 사후 보정 |
| **R6** | 과목 결정: 학생 선택 우선, AI와 불일치 시 `needsClassification` | AI 맹신 / 학생 맹신 | 학생 존중 + 재확인(human-in-the-loop) |

> **R6가 핵심 철학** — AI를 자동 실행기가 아니라 조수로 사용한다. 학생 선택을 최우선 존중하되, AI 판정과 다르면 강제로 덮지 않고 `classificationFailed=true`만 켜 **분류 수정 화면으로 재확인**을 유도한다.

### 동시성·정합성

- **동시 업로드 경합 방어** — `ProblemPersistence.saveUnderActiveLimit`이 "상한 확인 + INSERT"를 SERIALIZABLE 트랜잭션 하나로 실행한다.
  - **격리 수준은 새로 시작하는 트랜잭션에만 적용된다.** 호출부가 이미 트랜잭션 안이면 기본 전파(`REQUIRED`)는 그 트랜잭션에 합류하면서 SERIALIZABLE을 **조용히 무시**한다. 실제로 `/select` 경로가 `@Transactional`이라 이 상태였다.
  - 그래서 Persistence는 **`REQUIRES_NEW`로 항상 자기 트랜잭션**을 열고, 등록·선택 서비스 메서드는 트랜잭션 밖(`NOT_SUPPORTED`)에서 실행한다.
  - 같은 학생의 등록이 동시에 겹쳐 DB가 한쪽을 교착·직렬화 실패로 끊으면, 500 대신 **409 + 재시도 안내**로 응답한다.
- **"실패인데 등록됨" 완화** — 느린 OCR·분류는 **트랜잭션 밖**에서 수행(DB 커넥션 미점유)하고, `ANALYZE_DEADLINE_MS = 150,000ms`(FE 타임아웃 240s보다 짧게)를 OCR 완료 후·각 문제 분류 전에 확인해 서버가 FE보다 먼저 포기하도록 함.
  > 단, 이 마감은 **호출과 호출 사이에서만 검사하는 체크포인트**이지 하드 캡이 아니다. 마감 직전에 시작된 분류 호출이 read 80초를 다 쓰면 총 소요가 150초를 넘을 수 있다 — [한계와 다음 단계](#한계와-다음-단계) 참고.
- **중복 요청 차단** — `Idempotency-Key`(키별 락 + 10분 캐시). 등록은 헤더 키를 **학생별로 구분**해 쓰고, 선택은 `detectionId`를 키로 쓴다.
- **외부 API 안정화** — OCR connect 5s / read 80s, 기본 2회 시도 후 폴백 모델 1회. (상세: [AI 문제 인식 폴백](./AI-폴백-처리.md))

### 이미지 생애주기

이미지는 S3에 **먼저** 올라가므로, 안 쓰는 파일을 반드시 정리한다. 동시에 **써야 할 파일을 잘못 지우지 않는 것**도 같은 무게로 다룬다.

| 상황 | 처리 |
|---|---|
| 저장/캐시 **전** 실패(감지 0건·과목 혼합·짧은 글·페이지 인식 이상 등) | `committed=false` → **즉시 삭제** |
| 저장/캐시 **성공 후** 예외 | `committed=true` → **삭제 안 함**(유령 URL 방지) |
| 다중 감지 후 **선택** | 고른 문제의 장 + **어느 문제에도 배정되지 않은 장**을 저장. 다른 문제에만 배정된 장은 **1시간 유예 후** 삭제 |
| 장 번호를 **신뢰할 수 없음**(범위 밖 등) | 전부 저장 |
| 다중 감지 후 **10분간 미선택** | `ProblemImageCleanupScheduler`(10분 주기)가 `sweepExpired()`로 삭제 |
| 질문 **취소** | 학생의 명시적 요청이라 즉시 삭제 |

## 검증

동시성·트랜잭션 경계·접근 제어는 눈으로 확인하기 어려워, 재현 테스트로 고정했다.

| 테스트 | 무엇을 보장하는가 |
|---|---|
| `ProblemCreateTransactionTest` (1) | `createProblem`을 `NOT_SUPPORTED`로 둔 채 등록이 자체 트랜잭션으로 커밋되고, save 이후 **detached 엔티티의 LAZY `imageUrls` 접근에서 예외가 나지 않음** |
| `ProblemAccessControlTest` (6) | 토큰 없으면 401 · 역할 불일치 403 · 쿼리로 남의 ID를 넣어도 **토큰 주인 기준**으로 조회 · 남의 질문 조회·분류 수정·순서 변경·취소 403 · 본인과 강사는 조회 가능 |
| `ProblemSelectTest` (7) | 여러 문제 감지 시 저장하지 않고 학생에게 묶인 선택 대기 · **다른 학생 선택 거부 후에도 원래 학생은 선택 가능** · **같은 선택 동시 2회 → 1건만 생성** · 선택 등록과 Persistence가 **호출부 트랜잭션에 합류하지 않음** · 미배정 장 보존 + 제외 장 유예 삭제 · 장 번호 불신 시 전부 보존 · 저장 실패 시 재선택 가능 |
| `GeminiClientModeValidationTest` (6) | 1장 `SINGLE_MULTIPAGE` 보정 · 장 누락·중복 거부 · 여러 문제 묶임(선택지·EBS 코드) 거부 · 정상 케이스는 제안 순서로 조합하고 분류 1회 |

**테스트가 실제로 버그를 잡는지도 확인했다.** 고친 코드를 하나씩 옛 방식으로 되돌려(`permitAll` 복원, 소유권 검사 제거, Persistence를 `REQUIRED`로, `take`를 제거 없는 조회로, 모드 검증 3종 제거, 미배정 장 제외) 돌렸을 때 **8가지 모두 해당 테스트가 실패**했다.

> 테스트 프로파일은 H2 인메모리 DB와 `gemini.api.key=none`(OCR·분류 Mock)으로 동작한다.
> 그래서 트랜잭션 경계는 "새 트랜잭션이 열리는가"(바깥 트랜잭션을 롤백해도 등록이 남는가)로 검증했고, **MySQL에서 실제로 락이 겹칠 때의 409 변환은 테스트로 재현하지 못했다.**

## 선택한 대안과 버린 대안

| 결정 | 선택 | 버린 대안과 이유 |
|---|---|---|
| 동시 등록 상한 | `SERIALIZABLE`로 "개수 확인 + INSERT" 원자화 | **UNIQUE 제약** — "PENDING 3개까지"는 개수 조건이라 유니크 키로 표현할 수 없다. **애플리케이션 락** — 다중 인스턴스에서 무력. 등록은 초당 수 건 수준이라 SERIALIZABLE의 경합 비용을 감당할 수 있다고 판단. |
| 격리 수준 보장 방식 | Persistence를 `REQUIRES_NEW` + 호출부 `NOT_SUPPORTED` | **호출부만 `NOT_SUPPORTED`로 맞추기** — 누군가 트랜잭션 안에서 부르면 같은 문제가 재발한다. 격리가 필요한 컴포넌트가 스스로 보장하게 했다. |
| OCR·분류 호출 | 2단계로 **분리** 호출 | **1회 통합 호출** — 프롬프트가 비대해져 정확도가 떨어지고, 무엇보다 **분류 실패가 등록 실패로 번진다.** |
| 다중 감지 결과 보관 | 인메모리 `DetectionCache` + TTL | **재OCR** — 선택할 때마다 Gemini 호출이 한 번 더 발생(비용·수 초 지연), 결과도 1차와 달라질 수 있다. **DB 임시 테이블** — 10분 뒤 버릴 데이터에 스키마·정리 로직을 더하는 비용이 MVP 단계에서 과했다. |
| 같은 선택 중복 방지 | 캐시에서 **원자적으로 꺼내기** + `detectionId` 멱등 키 | **꺼낸 뒤 저장 후 제거** — 그 사이 두 번째 요청이 끼어든다. **중복 요청에 에러 응답** — 첫 요청은 성공했는데 사용자에게 실패로 보인다. |
| 장 인식 이상 시 | **거부**(다시 올리기) | **플래그로 확인 요청** — 수정 화면에서 본문을 편집할 수 없어, 확인해도 빠진 글을 되살릴 방법이 없다. |
| 선택에서 제외된 장 | 미배정 장은 보존, 나머지는 **유예 삭제** | **즉시 삭제** — 장 번호가 틀리면 원본을 잃는다. **전부 보존** — 강사에게 다른 문제의 장이 함께 보인다. |
| AI 판정과 학생 선택 충돌 | 학생 선택 우선 + `needsClassification` 플래그 | **AI로 덮어쓰기** — 학생이 맞는 경우를 뭉갠다. **학생 값 그대로 신뢰** — 오분류가 그대로 매칭까지 전파된다(R6). |

## 한계와 다음 단계

설계상 알고 있는 약점과, 운영 단계로 갈 때 손봐야 할 지점.

| 한계 | 영향 | 개선 방향 |
|---|---|---|
| 분석 마감이 **체크포인트**라 하드 캡이 아님 | 최악의 경우 총 소요가 150초를 넘겨 FE 타임아웃과 엇갈릴 수 있음 | 분석을 별도 스레드로 실행하고 `Future.get(timeout)`으로 강제 중단 |
| 모드 검증이 **뚜렷한 신호만 잡는 휴리스틱** | 신호 없는 오판, 한 문제를 여러 문제로 쪼개는 반대 방향 오판은 못 막음(유예 삭제가 피해만 줄임) | 장별 문제 번호를 응답 스키마에 포함해 구조적으로 검증 |
| `DetectionCache`·멱등 캐시·유예 삭제 대기열이 **인메모리** | 재시작 시 선택 대기 건 소실(유예 삭제 대상은 지워지지 않고 남음), 다중 인스턴스에서 미동작 | Redis 또는 삭제 예정 테이블로 이전 |
| 유예 삭제에 **사용자 복구 경로가 없음** | 운영자가 복구할 시간만 벌어줌 | 수정 화면에서 제외된 장을 다시 붙이는 기능 |
| 멱등 서비스의 `locks` 맵이 **evict되지 않음** | 키가 누적되어 점진적 메모리 증가(선택 요청도 이 서비스를 사용) | 응답 캐시와 같은 TTL로 함께 정리하거나 `Caffeine` 도입 |
| `SERIALIZABLE` 충돌 시 **자동 재시도 없음** | 409로 안내만 하고 사용자가 다시 시도해야 함 | 교착·직렬화 실패에 한해 짧은 백오프 재시도 |
| Gemini API 키를 **쿼리스트링**으로 전달 | 중간 로그에 키가 남을 여지 | `x-goog-api-key` 헤더로 전환 |

## 핵심 포인트

- **입구 6단계 가드(R1~R6)** 로 쓰레기·오분류·도배를 등록 전에 차단하고, AI 판정은 학생 확인으로 보정(human-in-the-loop). 그 전제로 **요청자를 토큰에서만 식별**한다.
- **"외부 호출은 트랜잭션 밖 + 격리가 필요한 곳은 스스로 새 트랜잭션 + 원자적 캐시 소비 + 멱등 키"** 조합으로 느린 AI·재시도·동시성이 만드는 정합성 문제("실패인데 등록"·이중 등록·상한 초과)를 막는다.
- AI 출력은 **분류뿐 아니라 구조(모드·장 번호)까지 믿지 않는다.** 성립하지 않는 판단은 보정·거부하고, 틀릴 수 있는 장 번호로는 이미지를 바로 지우지 않는다.
