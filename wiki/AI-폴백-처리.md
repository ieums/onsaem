# AI 문제 인식 폴백 처리

> 담당: 정수민
>
> 문제 사진 인식은 **외부 AI(Gemini)에 전적으로 의존**한다. 그 외부 의존이 흔들릴 때
> 사용자 흐름을 어디까지 지켜낼지 — **타임아웃 · 재시도 · 폴백 모델 · graceful degradation**의 4단 방어. `domain/problem`.

## 한눈에 보기

| 항목 | 내용 |
|---|---|
| 호출 구조 | OCR(이미지→텍스트)과 분류(텍스트→과목·단원·난이도)를 **별도 호출로 분리** |
| 일시 오류 판정 | HTTP **5xx 또는 429** |
| OCR 예산 | 기본 모델 2회 → 폴백 모델 1회 (connect 5s / read 80s) |
| 분류 예산 | 기본 모델 1회 → 폴백 모델 1회 (문제 수만큼 반복되므로 최소화) |
| 백오프 | 재시도 전 1초 → 2초 (선형) |
| 실패 시 동작 | **OCR 실패 = 등록 중단** / **분류 실패 = 기본값으로 등록 진행** |
| 전체 마감 | `ANALYZE_DEADLINE_MS = 150s` (호출 사이 체크포인트) |

## 문제 상황

문제 등록의 성패가 통제할 수 없는 외부 API에 묶여 있다.

- Gemini는 **과부하(503)·레이트리밋(429)** 로 수시로 실패한다.
- 그렇다고 무한정 재시도하면 사용자는 로딩 화면에 갇힌다. **프론트 업로드 타임아웃은 240초**다.
- OCR은 이미지 여러 장을 한 번에 보내 출력이 길다 — 정상 호출도 수십 초가 걸려 타임아웃을 짧게 잡을 수 없다.
- 분류는 **감지된 문제 수만큼 반복 호출**된다. 문제 5개면 호출도 5번이라 재시도 예산이 그대로 곱해진다.
- 무엇보다, **모든 실패를 똑같이 취급하면 안 된다.** OCR이 실패하면 등록할 내용 자체가 없지만,
  분류가 실패해도 문제 본문은 이미 손에 있다. 후자까지 등록을 막으면 사용자만 손해다.

## 해결 방법

### 1단계 — OCR과 분류를 분리 호출

한 번의 호출로 "텍스트 추출 + 과목·단원·난이도 판정"을 모두 시키지 않고 둘로 쪼갰다.

| 이유 | 설명 |
|---|---|
| **실패 격리** | 분류 실패가 등록 실패로 번지지 않는다. 이 문서의 핵심 전제. |
| **정확도** | 프롬프트가 짧아진다. OCR 프롬프트는 "절대 분류하지 마라"를 명시해 모델이 한 가지 일만 하게 한다. |
| **파라미터 분리** | OCR은 `temperature 0.1` · `maxOutputTokens 65536`(긴 지문 잘림 방지), 분류는 `temperature 0.2` · `8192`로 각각 최적화. |
| **모델 분리** | 두 단계의 모델을 따로 지정해 각각 교체할 수 있다. OCR은 빽빽한 한글 vision 작업이라 lite 모델이 반복 루프에 빠지기 쉬워 flash를 쓰고, 분류도 어려운 문제의 정확도를 위해 flash-lite에서 flash로 올렸다. |

### 2단계 — 재시도 (같은 모델, 백오프)

일시적 오류(**5xx / 429**)만 재시도한다. 4xx(잘못된 요청·인증 실패)는 재시도해도 같은 결과라 즉시 던진다.

```
OCR      기본 모델 ──(1s 대기)──> 재시도 1회      = 최대 2회
분류     기본 모델                                = 1회
```

> 분류의 재시도 예산이 1회뿐인 건 의도적이다. 분류는 **문제 수만큼 반복**되므로
> 여기에 재시도를 더하면 총 소요 시간이 문제 개수만큼 배로 늘어 FE 타임아웃을 넘긴다.
> 대신 아래 폴백 모델이 실질적인 두 번째 시도 역할을 한다.

### 3단계 — 폴백 모델 전환

같은 모델로 재시도해도 실패하면, **다른 모델**로 한 번 더 시도한다.
같은 모델을 계속 두드리는 것보다 가용성이 다른 모델로 갈아타는 편이 성공률이 높기 때문이다.

| 단계 | OCR | 분류 |
|---|---|---|
| 기본 모델 | `gemini.api.ocr-model` (기본 `gemini-2.5-flash`) | `gemini.api.model` (기본 `gemini-2.5-flash`) |
| 폴백 모델 | `gemini.api.ocr-fallback-model` | `gemini.api.classify-fallback-model` |

모델명을 **모두 환경변수로 빼** 코드 수정·재배포 없이 교체할 수 있다.
폴백 모델이 기본 모델과 같게 설정돼 있으면 전환을 건너뛴다(무의미한 중복 호출 방지).

### 4단계 — graceful degradation (분류 한정)

여기가 설계의 핵심이다. **OCR 실패와 분류 실패를 다르게 처리한다.**

| 실패 지점 | 처리 | 근거 |
|---|---|---|
| **OCR 실패** | 등록 중단 + 저장한 이미지 정리 | 문제 본문이 없으면 등록할 내용 자체가 없다. 빈 질문이 강사에게 노출되면 매칭 품질이 무너진다. |
| **분류 실패** | **기본값으로 등록 진행** + `classificationFailed=true` | 본문은 이미 확보됐다. 과목·단원은 학생이 수정 화면에서 고를 수 있다. |

분류 실패 시 채우는 기본값:

| 필드 | 값 | 이유 |
|---|---|---|
| `subject` | `UNKNOWN` | 과목은 학생 선택값이 우선하므로 비워둬도 무방 |
| `difficulty` / `totalDifficultyScore` | `MEDIUM` / `50` | 중립값 |
| `examType` | `UNKNOWN` | 추측하지 않음 |
| `summary` | **본문 앞 30자 + `…`** | 목록에서 무엇에 관한 질문인지는 보여야 함 |

> `summary`를 본문 일부로 채우는 건 타협이다. AI 요약이 없으면 목록이 비어 보이므로 원문 앞부분이라도 노출한다.
> **분류 폴백 모델을 도입한 결정적 이유가 이것이었다** — 폴백이 없던 시절엔 503이 날 때마다
> 분류가 실패해 목록에 요약 대신 **문제 본문이 그대로 잘려 나오는** 화면이 그대로 노출됐다.

### 실패 메시지 정제

외부 API의 raw 응답을 사용자에게 노출하지 않는다.

| 상황 | 사용자에게 보이는 메시지 |
|---|---|
| 5xx·429 (과부하) | "지금 AI 분석 요청이 많아 혼잡해요. 잠시 후 다시 시도해 주세요." |
| 그 외 실패 | "문제 분석에 실패했어요. 잠시 후 다시 시도해 주세요." |
| 전체 마감 초과 | "지금 AI 분석이 지연되고 있어요. 잠시 후 다시 시도해 주세요." |

## 검증

외부 API 장애는 원할 때 재현할 수 없어, **API 키가 없으면 Mock으로 동작하는 경로**를 코드에 심었다.

- `gemini.api.key=none`이면 `GeminiOcrClient`·`GeminiClassifier`가 Mock 결과를 반환한다.
- 덕분에 테스트 프로파일에서 **외부 호출 없이 등록 파이프라인 전체를 재현**할 수 있고,
  `ProblemCreateTransactionTest`가 이 경로로 트랜잭션 경계를 검증한다.
- 폴백 전환·백오프는 로그로 추적한다 — `OCR 기본모델(...) 과부하(503) — 폴백모델(...)로 재시도`,
  `분류 실패 — 기본값으로 등록 진행(문제 2/5)` 형태로 어느 단계에서 무엇이 일어났는지 남긴다.

## 선택한 대안과 버린 대안

| 결정 | 선택 | 버린 대안과 이유 |
|---|---|---|
| 재시도 간격 | **선형 백오프(1s, 2s)** | **지수 백오프** — 총 예산이 150초로 묶여 있어 지수 증가의 이점이 나오기 전에 마감에 닿는다. **즉시 재시도** — 과부하 상황을 더 악화시킨다. |
| 폴백 방식 | **다른 모델로 전환** | **같은 모델 재시도 횟수 증가** — 503은 모델 단위 과부하라 같은 모델을 두드려봐야 확률이 오르지 않는다. |
| 분류 실패 | **기본값 등록 + 수정 유도** | **등록 실패 처리** — 본문이 멀쩡한데 사용자만 손해. 과목은 어차피 학생 선택값이 우선이라, 분류가 비어도 수정 화면에서 보정할 수 있다. |
| 재시도 대상 | **5xx·429만** | **모든 예외 재시도** — 4xx는 재시도해도 같은 실패라 시간만 낭비하고 마감을 앞당긴다. |
| 모델 지정 | **환경변수** | **코드 상수** — 모델 과부하는 운영 중에 발생하는데, 교체하려면 재배포가 필요해진다. |

## 한계와 다음 단계

| 한계 | 영향 | 개선 방향 |
|---|---|---|
| 전체 마감이 **호출 사이 체크포인트** | 마감 직전 시작된 호출이 read 80초를 다 쓰면 총 소요가 150초를 넘을 수 있음 | 분석을 별도 스레드로 실행하고 `Future.get(timeout)`으로 강제 중단 |
| 분류가 문제 수만큼 **순차 호출** | 문제가 많을수록 시간이 선형 증가 | 병렬 호출(레이트리밋 고려한 동시성 제한 필요) |
| 폴백 모델까지 실패하면 **복구 수단 없음** | 사용자가 직접 재시도해야 함 | 실패한 등록을 큐에 넣고 비동기 재처리 후 알림 |
| 회로 차단기(circuit breaker) 없음 | Gemini 전면 장애 시 모든 요청이 예산을 전부 소진한 뒤 실패 | 연속 실패 임계치 도달 시 일정 시간 즉시 실패로 전환 |
| API 키를 **쿼리스트링**으로 전달 | 중간 로그에 키가 남을 여지 | `x-goog-api-key` 헤더로 전환 |

## 핵심 포인트

- **실패를 등급으로 나눈 것**이 이 설계의 전부다. OCR 실패는 치명적, 분류 실패는 degradable —
  이 구분이 있었기에 "AI가 반쯤 죽어도 사용자는 질문을 등록할 수 있는" 상태를 만들 수 있었다.
- 4단 방어(**재시도 → 폴백 모델 → graceful degradation → 마감**)는 각각 다른 종류의 실패를 담당한다.
  일시적 흔들림은 재시도가, 모델 단위 과부하는 폴백이, 부분 실패는 degradation이, 지연은 마감이 흡수한다.
- 모델명을 전부 환경변수로 빼 **운영 중 재배포 없이** 대응할 수 있게 했다.
